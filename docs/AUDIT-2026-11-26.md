## Executive summary

The repository was empty when the initial V1 scaffold was introduced. The current codebase is therefore a small starter application, not a pre-existing complete OSINT platform. No legacy OSINT database schema, user accounts, saved investigations, or third-party integrations were present to preserve.

The audit found one operational feature in source code: passive DNS record lookup (A, AAAA, MX, NS, TXT). The rest of the requested platform is not yet implemented. The UI explicitly labels most modules as planned; those labels must remain honest until each feature has a working backend and tests.

## Repository inventory

- `src/server.js`: Express server, Helmet headers, JSON body limit, API rate limit, health endpoint, module catalogue, passive DNS endpoint, static file serving.
- `public/index.html`, `public/app.js`, `public/styles.css`: responsive dark dashboard and DNS lookup form.
- `www/index.html`, `www/app.js`, `www/styles.css`: AppMint/WebView-oriented static shell. It links to the hosted app; it does not yet call a configured remote API itself.
- `test/smoke.test.js`: two small domain-validation tests only.
- `package.json`: Express, Helmet, express-rate-limit, Zod and pg dependencies. PostgreSQL client is installed as a dependency but is not used in application code.
- `render.yaml`: proposed Render web service and a separate free PostgreSQL database.
- `.env.example`: variable names only; no provider secrets.
- `README.md`, `docs/ARCHITECTURE.md`: starter documentation.

## Render and data safety findings

- The only existing PostgreSQL instance found in the workspace is `warworld-game-db` in Oregon. It belongs to the separate Warworld project and must not be connected to or modified by OSINT HUB.
- The OSINT Render Blueprint proposes a separate Frankfurt PostgreSQL instance and a Node web service, but the latest Blueprint read returned `resources: []`. No OSINT database or web service has been provisioned yet.
- The Render Blueprint is currently in sync with the repository definition; this does not mean the app is deployed or healthy.
- The Render free PostgreSQL plan may have lifecycle/expiry limitations. Confirm the current plan and expiry in Render before relying on it for persistent investigations.

## Security findings

Existing protections: Helmet security headers, 32 KB JSON body limit, 40 requests/minute API rate limit, Zod input parsing and a strict domain-name check for DNS.

Gaps before production: authentication and authorization, session lifecycle, CSRF strategy for cookie-authenticated writes, persistent audit logging, database parameterization policy, secrets-management workflow, upload validation/limits, SSRF-safe outbound HTTP policy, provider quota isolation, backup/restore procedures, and security tests.

The DNS endpoint is a passive lookup and does not scan target services. DNS failures are currently normalized to empty arrays, so the API does not yet distinguish “no record” from “resolver error”.

## Scope and privacy guardrails

People and contact intelligence must not become doxxing or tracking. No private-address discovery, account access, credential checking, real-time phone location, face identification, bypassing platform restrictions, or unapproved active scanning. Public data must be sourced and dated; correlation is not proof. Provider keys remain server-side.
